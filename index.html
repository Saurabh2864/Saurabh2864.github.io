CASE 01 LIMS-V1 · Test automation programme
Active · Deepak Cybit

End-to-end automation for an accredited laboratory system

Sampleify LIMS is a NABL & ISO compliant Laboratory Information Management System. Its data ends up on certificates of analysis for accredited labs, so input rules have to hold. I wrote the module-wise test-case workbook, then designed and built the Playwright + Python framework that runs it across browsers, in Docker and in CI, and reported the results to company leadership.

Role
Framework design, test design, execution, reporting
Platform
Web · Chromium, Firefox, WebKit
Scale today
205 automated tests in 15 modules (172 active, 33 skipped by design), built on 18 page objects
Period
2025 – present
Tools
VS CodePlaywrightpytestAllureDockerJenkinsGitHub ActionsGitGitHub
Challenge

Regression across Login, User Profile and 10 Organization Settings areas was manual, slow to repeat on two browsers, and hard to trace back to requirements.

Approach

Every workbook case became a test with the same ID. Page Object Model, data-driven inputs and one CI image that runs the same way locally, in Jenkins and in GitHub Actions.

Result

A full cross-browser cycle now runs unattended in about 3 hours, with screenshot, video and trace evidence for every failure.

Since the report

The figures below are from the full cycle of 4 Oct 2026. The suite has kept growing: it now has 205 test functions across 15 modules, adding Accounting Settings, Invoice Settings and Training Schedules, and CI runs Chromium on every push plus a nightly Chromium, Firefox and WebKit matrix.

Framework features

  • Browser, headed mode and base URL switchable from the command line
  • Markers for sanity, regression, data-driven and end-to-end runs
  • Screenshot, video and trace kept only when a test fails, attached to Allure
  • Self-contained HTML report alongside Allure results
  • Ready for parallel runs (pytest-xdist) and reruns of flaky tests
# tests/test_end_to_end.py  (excerpt)
@pytest.mark.end_to_end
def test_end_to_end_flow(page):
    email, password = perform_registration(page)   # 1. register with Faker data
    perform_logout(page)                           # 2. logout
    perform_login(page, email, password)           # 3. login as the new user
    add_product_to_cart(page)                      # 4. search "MacBook", add to cart
    verify_shopping_cart(page)                     # 5. assert the cart total

How I work

From requirement to release decision

The same five steps run through every case above, and each one leaves something a reviewer can check.

01

Understand

Read the requirement and confirm the unclear parts with the client or product owner before testing starts.

→ clarified spec
02

Design

Write module-wise test cases with IDs, covering positive, negative and boundary inputs.

→ test-case workbook
03

Automate

Automate stable regression with POM and data-driven tests; keep exploratory testing manual.

→ framework + suites
04

Run & prove

Run in CI on every browser, with screenshot, video and trace for each failure.

→ Allure evidence
05

Report

Group defects by theme and priority, and state the decisions needed for release.

→ report for leadership
